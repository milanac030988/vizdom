# Defense Q&A sheet

One line per likely committee question: the answer to give in one breath, then
the slide or table that backs it. Numbers are from lifecycle run 3 (controls and
grounders) and run 6 (`desc=` chain), both on a rented RTX 6000 Ada; every figure
traces to a result JSON under `benchmarks/results/` by run id and commit.

Slide numbers refer to `docs/present/index.html` (EN deck).

## A. The claim

**1. What is the contribution, in one sentence?**
A screenshot becomes a queryable, inspectable element tree that a test can
locate in, act on and assert against, parsed once per screen state. The
benchmark shows this tree says "no" when an element is absent, which the
per-step grounding models cannot do.
*Slides 21 and 29; `benchmarks/README.md` sec. 6.*

**2. Detection is a solved, commoditised problem. What did you add?**
Agreed, and the architecture treats detectors as interchangeable backends
(UIED, OmniParser, the modular stack). The contribution sits above detection:
hierarchy construction, roles, the locator surface, Robot Framework keywords,
the description resolver, and a lifecycle benchmark with a false-pass metric.
*Slide 29; ADR-022, ADR-024, ADR-027.*

**3. Why not simply use UI-TARS or Aria-UI? They hit more clicks.**
They do: 0.944 and 0.962 action-hit against our 0.934. But as test oracles they
pass 60 and 88 of 88 absent elements, so a suite built on them cannot fail for a
missing control. They also return a point, not an element: no text, role, count
or `within=` scoping. And each step is a fresh 1.6 to 4.0 s inference versus one
parse per state plus a sub-millisecond lookup.
*Slide 11 (economics), slide 21 (table); README sec. 6 main table.*

**4. Is 0.934 action-hit good enough for real testing?**
On this benchmark the remaining misses are detector misses (an element the
parser did not box) or ambiguous labels, not resolver errors. The honest answer
is that the number is for clean synthetic screens. The real-application work
(Calculator demo, the enterprise screen on slide 26) shows the same pipeline
working, but unmeasured. A real labelled set is the first item of the roadmap.
*Slides 19, 26, 30, 31.*

## B. The benchmark

**5. The screens are synthetic. Why should we believe the numbers transfer?**
We do not claim the absolute values transfer; we claim the ordering and the
oracle property do. The synthetic set gives exact ground truth, 514 steps with
zero manual annotation, and reproducibility: the DOM columns are bit-identical
across four runs on three cards. The grounders moved by one point between GPUs
even with greedy decoding.
*Slide 19, slide 30; README run-history table.*

**6. The negatives are nonsense words like "Frobnicate". Isn't that easy?**
Yes, these are the easiest negatives, and the grounders still passed 68 to 100 %
of them. Plausible-but-absent labels ("Export" on a screen that has "Import")
are the harder test and are listed as the next step, for VizDOM's OCR as much
as for the grounders.
*Slide 30 (limitations); README "Planned extensions".*

**7. How are the test steps derived? Could the derivation favour VizDOM?**
Every actionable element whose caption is unique in its state becomes an action
step and a positive verify step, from the element ground truth, no hand
labelling. Each step carries both forms: a locator for DOM systems and an
instruction ("click the 'Save' button") for grounders, so each side gets the
task in its native form. The grounders judge from the same screenshot.
*Slide 21; README sec. 3.*

**8. What does "false pass" measure and why does it matter more than hit rate?**
A PASSED verdict on an element that is not on the screen. In testing this is the
worst outcome: the suite is green while the defect is on screen. Agent
benchmarks score clicks only, so this failure mode is invisible there. Our
columns: 0 of 88 for every DOM column, 60 to 88 of 88 for the grounders.
*Slide 21; README sec. 5 metrics.*

**9. Verify accuracy 0.964 counts a wrong element as correct. Is that cheating?**
It is a known weakness of the verify metric and it is documented: a positive
verify passes if any element resolves. One such case exists in run 6
("Cancel" resolved to the × icon on a dialog whose Cancel text OCR had not
read). Action-hit catches it, which is why both numbers are always quoted
together. A strict variant (resolved element must overlap the target) is in the
paraphrase check script.
*README sec. 6, desc chain bullet; `src/visual_dom/evaluation/lifecycle/paraphrase.py`.*

**10. The descriptions were generated by the same code that drew the screens.**
Correct, so the `desc=` row on them is an upper bound, and we measured the gap.
All 514 steps were re-resolved over the same run-6 DOMs with two hand-written
wordings: terse, as a tester types ("Save", "search box"), and wordy, which
drops the label or the role word ("the button that saves the changes"). Terse
costs three points of action-hit, wordy costs twenty-two, and the false-pass
rate stays zero in every wording. On the wordy set the lexical tier alone hits
0.11; the model tier behind it lifts that to 0.71. The weak spot it exposes is
wrong-element answers at high confidence, 24 of 213 actions.
*README sec. 6 paraphrase bullet; `benchmarks/lifecycle-synthetic-v1/paraphrases.json`; table at the end of this sheet.*

**10b. Your pipeline combines several models and stages. Which parts actually matter?**
We left them out one at a time on the same detector and the same 514 steps
(ablation, README sec. 7, slide 16c). Without OCR nothing resolves: every
button is still boxed and the action-hit is 0.000, so language carries the
test. Plain OCR without upscale and the Tesseract retry costs 12 hits. Role
recovery is invisible to `text=` steps but drops typed accuracy from 0.91 to 0
and costs 1.4 points under `desc=`. Label association, the glyph reader and the
SLM refiner change nothing on clean synthetic screens; the first two were built
for real screens and are not exercised here, the refiner costs 3.2x parse time
for nothing and stays off. Smart merge costs detection F1 on this set and buys
nothing a test sees, which is now a known over-merge to revisit.
*README sec. 7; slide 16c; ADR-012 history 1.1.*

**10c. Your laptop numbers are higher than the GPU numbers for the same column. Why?**
The Tesseract retry only looked for a Windows install, so it never ran on the
rented Linux hosts. The published GPU rows are therefore lower bounds for the
VizDOM columns, measured and quoted as such with commit and host; the grounder
rows are unaffected. The lookup is fixed and the kit installs the binary; a
rerun would lift the VizDOM rows by about three points.
*README sec. 7 host finding; ADR-012 1.1; `deploy/gpu/setup.sh`.*

## C. Models and the description tier

**11. Why a 3B model? Would a larger one not be better?**
The design goal is that the model is a fallback, not the path: the lexical tier
answers 398 of 514 steps with no model at all, the SLM is called on 116 and
answers 6. A 3B model runs on a laptop CPU and costs 0.2 s a call. Larger
models would raise the SLM-only row (0.667) but that row is not the product
configuration. 7B tiers are on the list for a later run.
*Slide 27; README desc table; ADR-022.*

**12. What went wrong with the vision tier?**
Two things, both documented. The 3B vision model collapses into a repeated
token on a fixed set of screens; Ollama aborts the generation and the step is
an error (80 of 116 calls in the lexical+vlm column). On the calls it answers,
it passes 17 of 30 negatives at confidence 0.95, so it is not an oracle. The
tier stays opt-in. The claim to make: implemented, measured twice, not an
oracle, not the default.
*README "run-6 vision" bullet; ADR-022 history 1.3.*

**13. Why did the single false pass in run 4 disappear in run 6?**
A one-row shortlist turns "which of these matches?" into "is this it?", and a
3B model says yes to a plausible name ("Purple Elephant button" at 0.85). The
shortlist is now padded to at least three rows; the same step declines at 0.00
in run 6. The fix is a unit test, not a prompt change.
*ADR-022 history; `desc_resolver.py` SHORTLIST_MIN.*

**14. You changed the prompt between runs. Is the result prompt-sensitive?**
The chain is not: lexical answers 398 steps deterministically and run 6
reproduced run 4 on 509 of 514. The SLM-only column is: an explanatory null
rule made the 3B model answer nonsense captions 6 of 6 times over a whole-DOM
table, so that row fell from 0.020 to 0.126 false-pass. The prompt was reverted,
and the production chain never shows the model a whole DOM.
*README SLM-alone bullet; commit 0913715.*

**15. Does the model make the system non-deterministic?**
Only on the 116 steps that reach it, at temperature 0, and every answer is a
choice among listed element ids, never a coordinate. A miss is explained
("no confident match (slm not confident (0.00))") and the suite fails loudly.
The lexical tier and the DOM are deterministic and diff-able.
*Slide 11 reason 2 and 3; slide 27.*

## D. Architecture

**16. Why hexagonal with optional gRPC? It seems heavy for a library.**
Modifiability and deployability were ranked above accuracy for a greenfield
extensibility project, and the decision was scored: option C won 82 to 70 on
weighted criteria, losing on complexity, which is mitigated by in-process
being the default. Evidence: four detectors, five captures, three actuators,
each one file plus one registry line.
*Slides 14, 15, 18; ADR-015/017/018/019.*

**17. Which quality scenario failed?**
Accuracy: F1 0.58 against a target of 0.80 on the aggregate, which is text-
dominated. Per-type recall on actionable controls is 0.83 at IoU 0.5 and 0.97 by
center-hit. Logged as a risk, not reframed.
*Slide 18, slide 20.*

**18. What was the hardest engineering bug?**
Targeting the right window. Whole-screen capture and absolute-coordinate
actuation are silently wrong when the app is not in front, and the DOM cannot
tell. The fix is an optional port capability with a Win32 escalation and a
verified foreground read, so a refused focus fails the test loudly.
*Slide 28; ADR-021.*

## E. Limitations and next steps

**19. What would you do with three more months?**
In order: a real-application labelled set in the same schema; plausible-absent
negatives; descriptions written by other people; a vision model that does not
loop; error bars on the grounder columns. The code side: self-healing locators
that cache a resolved description as a deterministic alias.
*Slide 31; `paper/README.md` list.*

**20. Where is the work published or reusable?**
Repository with a documentation site, 25 ADRs, an arc42 document in two
languages, a Robot Framework library, the benchmark manifest and the result
tarballs. A conference paper draft (IEEEtran, 7 pages) exists with the oracle
claim; venue after the real-world rows.
*Slide 29; `paper/`.*
