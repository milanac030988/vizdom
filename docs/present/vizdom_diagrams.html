Component view · hexagonal architecture

The core never imports an adapter — every backend is chosen by name, locally or behind a service

This is the hexagon from ADR-017 to ADR-019. Top: four ways in, all through the pipeline. Middle: the core and its ports. Below the ports: local adapters and the gRPC clients. Bottom band: the three services. Point at the curved arrows: a service does not reimplement anything, it calls the same registry and drives the same adapters that sit above it, just on a different machine.

Deployment view

Perception where the GPU is, capture and input where the app is

Three colours, three services, three ports. The detector service loads the heavy model once and can serve several runners. Capture and actuator live next to the app because that is where pixels and input are; they do not need a GPU. The white box is the AUT: a Windows app, an Android app through adb, or a closed device under a camera. It is never modified, which is the whole point for a BSH-style target.
Deployment view · a closed device

Same two contracts, different hardware: a camera grabs, a robot arm taps

This is the case the actuator port was designed for (ADR-019). Top path: the capture service is a camera; the only new work is step 0 of the pipeline, which finds the screen in the photo and warps it flat. Bottom path: a Tap arrives as normalized coordinates with the image size, and the plugin's homography turns image pixels into arm coordinates. Be clear about status: the camera side runs today; the arm plugin is a worked stub that prints, and a real arm needs its driver, a calibration routine and its own e-stop.
Reference · protos/*.proto

The three gRPC contracts, call by call

ServiceCallWhat goes in · what comes backPort
DetectorDetectencoded image + optional box_threshold, text_ensemble → detections (bounds, visual_type, confidence, text, source), backend name, infer_ms:50051
HealthCheck→ ready, backend, model info — what the Viewer's Services window polls
CaptureGrabwindow_title (empty = full screen) → PNG, size, strategy, grab_ms, and the window's origin and device size for coordinate mapping (ADR-021):50053
Focustitle → focused only when the server verified the app is in the foreground, plus a detail string
HealthCheck→ ready, strategy, platform
ActuatorTap · Scroll · Swipenormalized nx, ny in [0,1] + the image size they were computed on → the server maps them to its own device pixels:50054
TypeText · PressKeytext or a key chord such as ctrl+a → ok, actuator name, action_ms
Focus · HealthChecksame focus semantics as capture; ready, actuator, platform

Every request carries a request_id, so one test step can be traced across all three services' logs. Field numbers are the versioned contract: new fields are appended, never renumbered. Each server installs a graceful shutdown handler, so a stop finishes in-flight calls before the model is released.

Two design choices worth saying out loud. Coordinates are normalized, so a DOM built on a cropped window still clicks the right pixel on a second monitor with negative coordinates. And the capture service returns geometry with the frame, which is what makes that mapping possible without the runner knowing the screen layout.

Follow the colours: blue to capture, orange to the detector, pink to the actuator. The green self-calls are the CPU work in the robot process. Detector backends are plug-ins, and one of them is built from stages

Left: the registry, five names. Right: what "modular" means. Stage 1 proposes boxes with real scores, stage 2 is the same OCR instance the pipeline already has, fusion is a faithful port of OmniParser's overlap rule, and the captioner is optional. The parity numbers come from the benchmark on the session screenshots.
Flow · ADR-022 · ADR-024

From a locator to exactly one element, or a loud failure

Read it as a funnel. The deterministic finder handles most locators with no model at all; in the Calculator demo every key resolves on text= and never reaches desc=. The grounding tiers are the fallback for controls with no text, and the demo pins the lexical tier so the run is reproducible.
Deployment view · vizdom.config.json

The same suite, four deployments — the config is the only difference

1 · one laptop

Everything in the robot process

"detector": { "backend": "uied" },
"capture":  { "strategy": "windows",
              "window_title": "Calculator" },
"actuator": { "strategy": "desktop" }

No service, no GPU. The CPU detector; good for authoring tests and for CI smoke runs.

2 · shared GPU

Perception moves to a GPU box

"detector": { "backend": "grpc",
  "grpc_target": "gpu-box:50051" },
"capture":  { "strategy": "windows" },
"actuator": { "strategy": "desktop" }

One warm OmniParser or modular server serves every tester's laptop. The model loads once.

3 · fully distributed

The demo: three machines

"detector": { "backend": "grpc",
  "grpc_target": "gpu-box:50051" },
"capture":  { "strategy": "grpc",
  "target": "sut:50053",
  "window_title": "Calculator",
  "window_scope": true },
"actuator": { "strategy": "grpc",
  "target": "sut:50054" }

The runner holds no model and never touches the SUT's screen directly. Failure screenshots come from the SUT.

4 · closed device

Camera in, robot arm out

"detector": { "backend": "grpc",
  "grpc_target": "gpu-box:50051" },
"capture":  { "strategy": "camera" },
"actuator": { "strategy": "robot-arm" }

An appliance panel with no OS access: the capture service reads a camera, an actuator plugin drives a finger. Same keywords, same DOM.

Strategies 1 to 3 run today (the Calculator suite passed 2/2 in deployment 3). Deployment 4 uses the camera capture that exists and an actuator plugin slot that is auto-discovered; the robot-arm driver itself is the part still to write.

Close on this one. The point of the hexagon is that these four are one code base and one test suite. Be honest about the fourth: the camera strategy and the plugin mechanism are there, the arm driver is not.
