The problem: automation stops where the tree stops

GUI test tools (Appium, Selenium, UI Automator) drive an application through its accessibility tree. It is the gold standard — when it exists.

Where it does not exist

  • custom-rendered Qt / QML / OpenGL canvases, game engines
  • embedded & industrial HMIs, automotive infotainment
  • any screen observed through a camera or video stream

Today's fallback

Coordinate scripts and image matching — no element semantics, and they break on any layout, theme, or resolution change.

The premise

A human tester looks at the screen and knows what is clickable. If a human can, a machine should be able to — from pixels alone.

Why GUI element detection is hard

Element level

  • Large intra-class variation — one button varies in size, shape, colour, styling
  • High inter-class similarity — a button vs a spinner differ by a thin border or a small glyph

GUI level

  • Heterogeneous mix — widgets, images and text abut each other
  • Dense, adjacent elements — separated by a few pixels
  • High-precision regions required — a loose box is fine to recognise an object, not to click a control

Taxonomy after Xie et al., Object Detection for Graphical User Interface: Old Fashioned or Deep Learning or a Combination? (FSE 2020) — the paper our group studied.

A sixth difficulty, specific to testing (ours)

Non-text elements have no name. The five above are about finding elements; automation must also name them — and toolbar icons, window controls and operator keys carry no readable text. Detection can localise such a control perfectly and still leave nothing to write in a locator. The three default answers all fail: position is brittle (breaks on relayout), OCR returns nothing (or glyph noise), and a caption model returns a prediction we measured to be unstable — ≤7/255 pixel noise flipped “Maximize” into “Page”.

1 · The test-loop economics

A grounder answers one instruction at a time: every click and every assertion is a fresh large-model inference. A parser pays perception once per screen state, then every lookup is an in-memory query.

Benchmark run: 44 states, 514 stepsModel callsPer-step cost
VizDOM (parse once per state) 44< 1 ms lookup
Grounder (per instruction)514 one GPU inference

Cost scales with screen states, not with test steps. Measured on a rented RTX 6000 Ada: VizDOM pays load once (2.6 s UIED / 8.1 s OmniParser) + 44 parses (0.39 s / 1.02 s per state) + 514 sub-millisecond lookups — 0.04–0.10 s per step amortised. A grounder pays 514 inferences at 1.6–4.0 s each (Aria-UI / UI-TARS / ELAM): 15–39× the per-step cost for the same suite.

Reuse economics: one parse serves many locators and assertions — the artifact is reused, the inference is not repeated.

2 · Four reasons beyond speed

  • Output shape. A grounder returns a point. A test also needs to assert existence, read an element's text/role/state, count matches, and express within=Form — a coordinate answers none of these.
  • Determinism. A test must fail for a real reason. We measured the failure modes directly: caption flips from imperceptible pixel noise, and a 3B model calling a top-left element “top right” at 0.95 confidence.
  • Explainability. When CI goes red you need why — an inspectable, diffable DOM versus a coordinate from a black box.
  • Hardware & licence. Our CPU path runs the full suite with no GPU and no network (Q-04); grounders are GPU-bound. Licences are Apache-2.0 or unverified — so we keep the model behind a swappable port.

Also: their published scores (ScreenSpot, OSWorld) measure a different task — instruction grounding, not element enumeration. They cannot be pooled with detection F1.

Not either/or — we use grounding where it pays. The desc= locator's Tier 2 is a VLM grounder, invoked only for the long tail that deterministic tiers cannot resolve, and snapped back onto a DOM element via Set-of-Mark. Roadmap: plug a dedicated grounder (Aria-UI / ELAM class) in as an alternative Tier-2 backend behind the same interface. Parse once for structure; ground only what is left.

Naming what has no text

The operator keys carry no readable label. The symbol reader (ADR-011) reads ÷ × − + = . structurally — not as OCR characters — and the DOM assigns the canonical name: Divide, Multiply, Minus, Plus, Equals, Decimal. Window chrome is named from its caption: Minimize, Maximize, Close. Each becomes a stable desc= target.

Stated plainly: composite glyphs (x², ²√x, ⌫) still get unstable captions — which is exactly why every locator in the demo is a text= || desc= fallback chain, not a single guess.

Locating by description — desc= in action

Every key is a fallback chain: the free, deterministic text= lookup runs first; desc= is reached only when it misses or is ambiguous — the measured failure cases (an OCR misread of a small glyph), not a guess. The operator keys have no readable label, so their description resolves against the name the DOM assigned:

Click Visual    desc="divide button"
→ E33  text="÷"  label="Divide"  ·  tier=lexical  score=3.00  ·  candidates E33, E9, E11 …

Resolved by the lexical tier — no model, deterministic, cached per screen; every hit records which tier answered. The SLM / VLM tiers stay available for the long tail, but the demo pins lexical so CI is reproducible.

Parse once, act many

Suite Setup dumps the DOM once; every click resolves against the cached DOM and taps. The second test re-uses it — no re-open, no re-capture — only the result is read back from the live screen.

The CV pipeline

  1. Text detection — OCR (EasyOCR / PaddleOCR / Tesseract), upscaling for small text
  2. Element detection — pluggable backend (UIED / YOLO / OmniParser)
  3. Merge & deduplicate — NMS, cross-type suppression, smart-merge of over-segmented labels
  4. Symbol reading — glyph operators OCR cannot read
  5. Reading order — top→bottom, left→right
  6. Optional SLM review — split / retype / merge / label
  7. Hierarchy — containment, alignment, label association
  8. DOM compile — roles, flags, multiple locators

Every stage threshold is resolution-aware (defined at 1080p, scaled up) and driven by one JSON session config.

Architecture drivers — ranked, and why

Method: SWA / arc42 — drivers → solution → documentation → verification. Every significant choice traces to a ranked driver.

RankDriverSpecific interpretation
#1Modifiability new detector / capture / actuator with no core changes
#2Deployability ports runnable in-process or remote by config
#3Testabilityfull runs with no GPU, no network
#4Accuracydetection F1 / IoU on real UIs
#5Performancewarm-model reuse; per-request latency
—Offline operation constraint: proxy blocks public hosts → vendoring, offline docs
—No containers constraint: distribute without Docker / orchestrators

This is a greenfield applied project whose stated purpose is extensibility across detectors and devices — so modifiability and deployability rank above raw accuracy. Were VizDOM a fixed single-platform product, accuracy and reliability would rank first.

Driver conflicts — and how they were resolved

Accuracy vs Testability. The most accurate detector (OmniParser) needs a GPU and ~1 GB of weights — conflicting with "runs on a laptop".

→ Resolved by making the detector a port: a CPU baseline (UIED) for laptops, plus a remote GPU service when accuracy matters.

Deployability vs Simplicity. gRPC services add moving parts to every run.

→ Resolved by making gRPC optional: in-process is the default, so the simple case pays nothing.

Both conflicts are resolved by the same mechanism — the port abstraction — which is why one pattern is applied to all three driven ports.

Solution space: classical, deep, or a combination?

Classical CV

Edge/contour aggregation, template matching. Training-free, interpretable, tight boxes — weak on artificial widgets and images.

Deep learning

Anchor-based (Faster R-CNN, YOLO) and anchor-free (CenterNet). Better coverage; bounding-box precision limited by feature-map regression.

Combination ✓

Classical region proposal for accurate non-text boxes + deep models for text and semantics. The UIED finding — and our architecture.

How VizDOM operationalises the question

  • GUI text is scene text, not document text — dedicated OCR, not one model for everything
  • Non-text and text detected by separate specialised paths, then merged
  • The detector is a pluggable port — so "classical vs deep vs combination" becomes a runtime configuration choice, and the answer is measurable per element type

The key decision — scored, not asserted

How should detection / capture / actuation be made extensible and deployable? Three alternatives, scored 1–5 against criteria weighted from the ranked drivers:

CriterionWeight A · hard-coded per consumer B · shared library, in-process only C · strategy + registry + optional gRPC
Modifiability51 (5) 4 (20)5 (25)
Deployability51 (5) 2 (10)5 (25)
Testability42 (8) 4 (16)5 (20)
Complexity lower better3 4 (12)4 (12) 2 (6)

Weighted total 457082

Scoring. Each cell = raw score 1–5, with (weighted contribution) in parentheses; total = Σ weight × score. Weights derive from driver rank (5 = top driver). For the two "lower is better" criteria a high raw score means low complexity.

Outcome: Option C. It wins decisively on the two top drivers, at the explicitly accepted cost of higher intrinsic and operational complexity — mitigated by keeping gRPC optional (Option B's behaviour is the default local mode) and by sharing one registry pattern across all three ports. Recorded in ADR-015 / 017 / 018 / 019.

Architecture overview · hexagonal + microservice-oriented

Component view · hexagonal architecture

The core never imports an adapter — every backend is chosen by name, locally or behind a service

Microservice-oriented, not always-on microservices

Each port is a first-class service boundary — a versioned protobuf contract plus a standalone gRPC server:

ServicePortRuns where
Detector50051GPU host — one warm model, many clients
Capture50053the device under test
Actuator50054the SUT / a robot-arm controller

Coordinates on the wire are normalized [0,1] + image size, so the protocol is resolution-independent; each strategy maps to its own device space (a robot arm applies a calibration homography).

Why distribute at all

  • independent scaling of the heavy model
  • heterogeneous placement (device / GPU / controller)
  • fault & resource isolation
  • polyglot substitution behind one contract

But in-process is the default. gRPC is a transport, not a requirement — the same services collapse into one process when co-location suffices, so we avoid the operational tax on the common case.

Evaluation: methodology & dataset construction

Four measured axes

  • Element detection — precision, recall, F1, mean IoU
  • OCR — character accuracy, CER / WER
  • Hierarchy — containment & label association needs tree GT
  • Locator quality — uniqueness, stability future

Greedy matching by IoU at 0.5, pooled over all elements. Computed by the project's own harness (visual_dom.evaluation).

No public benchmark fits — so we built one

  • Programmatic synthesis — templates × themes × resolutions with exact ground truth → 167 train / 44 test at 1920×1080
  • LLM-designed layouts — an LLM as UI designer (e.g. car infotainment) for structural diversity
  • Camera-style augmentation — perspective, glare, blur, noise; exercises the screen-rectification path

Only the clean synthetic split is scored. The other layers are development / robustness aids.

Testing effectiveness, end to end — one unified benchmark

Stage metrics grade a component. A test suite lives or dies on the whole lifecycle: locate → act → verify. So every system under comparison runs the same 514 steps over the same 44 states and is scored on the same outcomes.

How the steps exist at all

  • Derived from the element ground truth — zero new annotation: every actionable element whose caption is unique in its state becomes a step
  • Dual representation — a locator for DOM systems and an instruction ("click the 'Save' button") for grounding models, so both receive the task in their native form
  • Negative oracle steps — 88 deliberately absent captions expecting FAILED

That last one is the testing-specific metric: an agent benchmark asks did it click correctly; a test benchmark must also ask does it judge correctly — a false pass is the worst failure a test system can produce, and agent benchmarks do not measure it.

New capability — locating by description

Property locators break exactly where perception is weak. So the tester can state intent: Click Visual  desc="settings button" — importing the grounder paradigm into the parser system, with the DOM as source of truth.

Tier 0 · lexical

No model. Token/synonym overlap + role words + positions. Accepts only with a score floor and a margin — ties escalate rather than guess.

Tier 1 · SLM over DOM

Small text LM (temperature 0) picks an id from a compact element table. The id is validated against the DOM — hallucinations rejected.

Tier 2 · VLM Set-of-Mark

Candidate boxes are numbered on the screenshot; the model picks a number. Multiple choice beats coordinate regression — and the answer is a DOM element by construction.

5/5 probe descriptions resolved on a real session (paraphrases via the SLM tier); a nonsense description failed loudly with the candidate list.

Finding: a 3B model confidently called a top-left element “top right”. Positional words are therefore enforced geometrically, before any model — position is never delegated.

Determinism is policy: the tier chain is configured (CI can pin lexical-only), results cached per screen, and every hit records which tier answered — making “parse once, ground the long tail” measurable.

Composes with fallback chains. text=Save || desc="save button in the toolbar" — the deterministic locator runs first (free); desc= is reached only if it fails or is ambiguous. A fallback win logs a warning naming the stale primary, which is exactly the signal the planned self-healing locators need (ADR-024).

  • Now — added OmniParser's caption to disambiguate checkboxes and re-tuned the button/icon width boundary
0.09 → 0.87actionable type accuracy

Checkbox (0.55) remains weakest — recovered only when the caption is distinctive. Future work.

Improvement 2 — reading glyphs OCR cannot

Problem. Operator keys (+ − = × ÷) read as garbage: OCR fails on small glyphs, and the rule-based detector (projection profiles over the whole button) failed on every real calculator key — and false-fired + on the hollow maximize □, whose edge rows average to a central cross.

Redesign: template matching on the tight glyph

  1. upscale (anti-aliased strokes dissolve at native size)
  2. binarize, crop to the glyph's own bbox → scale-normalised
  3. reject hollow outline shapes structurally
  4. Dice-match against font-rendered templates, accept only a confident, unambiguous best

Second iteration — a thicker-glyph theme broke it again. The binarizer was choosing the wrong candidate: an adaptive-threshold ring artifact (glyph as a hole in a blob) scored best on the density heuristic, so a fat × matched the filled-dot template. Fix: score every binarization through template matching and keep the best — rings match nothing; plus a size gate for . and bold templates.

Improvement 3 — what is read vs what is inferred

A measured finding

Two captures of the same UI, visually identical, differing only by imperceptible re-encoding noise (≤7/255 per channel, ~90% of pixels), flipped an icon caption from “Maximize” → “Page”.

Deterministic within a run — so it is input sensitivity, not sampling. The maximize glyph is a bare square □: genuinely ambiguous to the caption model.

Diagnosed by re-running current code on the old capture: the regression was not in our code. Detector confidence sensitivity (a faint minimize dash falling just under a 0.05 cutoff at a different scale) was a second, separate finding — now a config knob.

The fix: split the two channels

A close button now reads text='×', label='Close'; an unreadable glyph has text=None and keeps its caption as a best-effort label.

Testing guidance: locate text-bearing controls by text=; icon-only controls by role= + spatial relations. A visual caption is a hint, not a stable id.

Two of our own bugs, not the model's

Missing status rows: the OCR ensemble only gap-filled — where OmniParser's native OCR had a garbage read in an 8 px box (~ctive for “Active”), our better read was skipped as a duplicate, and the tiny box then died in the size filter, deleting the row.
Split tiles: our splitter divides any control holding 2+ OCR boxes — EasyOCR emits word boxes, so “Check Now” became two half-buttons (Tesseract emits line boxes, which is why the defect appeared only with EasyOCR).

Fixes

Ensemble is now a prefer-external union (our upscaled read replaces an overlapping weaker one). The splitter never splits a control the detector marked as one interactable, and otherwise requires a real gap (≥1.5× text height) between texts. A configured-but-missing OCR engine now fails fast instead of silently degrading.

Outcome: the recommended combination is now unambiguous — OmniParser + EasyOCR wins every column, with no regression on the calculator or synthetic sets.

A correctness bug that no detector can fix — targeting the right window

Two design choices make the system portable: it captures the whole screen and actuates by absolute coordinate. Both are silently wrong the moment the application under test is not the front window.

What goes wrong

  • A grab photographs whatever is on top → a DOM of the wrong application
  • tap() hits whatever window is at that point; typed text follows keyboard focus → input delivered elsewhere
  • Undetectable from the DOM: the coordinates were correct for that screenshot, and the screenshot was correct for its moment

The fix — a port capability

  • focus_target(title) on both driven ports — optional hook, default no-op, so no plugin is forced to implement it
  • Win32 escalation (restore → borrow the foreground input queue → synthetic modifier tap → temporary top-most); wmctrl/xdotool on X11; am start on Android
  • Exposed as Bring App To Front (fatal) or focus_before_capture (warn-only)

Verify, never assume. The promoted code returned true whenever it had not thrown — which cannot tell “raised” from “the OS refused”, the exact case that yields a wrong screenshot. Now the strategy re-reads the actual foreground window; an honest false is what lets a test fail loudly.

Focus happens where the screen is. A client on another host cannot raise a window it does not own, so focus travels as its own Focus RPC — otherwise the feature would be missing from the one configuration the reference demo uses (capture and actuator over gRPC).

Off by default, because raising a window is an action — it can dismiss tooltips and transient popups, so it must never be implied by a read. Ambiguity fails with its candidate list rather than driving a coin-flip window.

Contributions & positioning

What is genuinely distinctive

  • Hierarchy construction — containment, alignment and label association compiled into a queryable tree; no compared system produces one
  • Testing orientation — locators, assertions, Robot Framework keywords
  • Reuse economics — one parse serves many locators and assertions, whereas grounders re-infer per instruction
  • Explainability — an inspectable tree with traceable matching rules, versus a coordinate from a black box

Engineering deliverables

  • Hexagonal engine, 5 ports, 3 as optional gRPC services
  • 25 ADRs; arc42 architecture document (EN + VI)
  • Robot Framework library; interactive Viewer; evaluation harness
  • Labelled benchmark + augmentation & LLM data-generation tooling
  • Unified lifecycle benchmark — 514 auto-derived steps, dual locator/instruction form, false-pass metric: parsers and grounders in one table
  • Published documentation site; runnable Windows demo

Detection is a commoditised layer — an industrial lab converged on the same decomposition. We therefore treat detectors as interchangeable backends and contribute in the layers above.

Limitations — stated plainly

Benchmark report Threats to validity

  • Synthetic, clean benchmark. Absolute scores will differ on gradient-heavy real-world UIs. A real labelled set is the top priority.
  • F1 target not met. NFR5 targets F1 ≥ 0.80 / mIoU ≥ 0.60 — mIoU is met (0.67–0.68), F1 is 0.51–0.58. Aggregate F1 is text-dominated; per-type recall on actionable controls (0.83 / 0.97 center-hit) is the meaningful figure.
  • Checkbox roles weakest (0.55) — recovered only when the caption is distinctive.
  • Caption instability on small glyph-only icons is inherent to the caption model; mitigated by the text/label split, not eliminated.
  • Hierarchy & locator axes not yet scored — the ground truth is a flat list with parent references, no tree, no locators.
  • Wall-clock measured on three rented hosts only. The DOM columns reproduce bit-for-bit across cards; grounder latency is host-dependent (UI-TARS 1.7–2.7 s/step) and their scores move ±1 point between GPUs even with greedy decoding — every number is quoted with commit and machine.
  • Negatives are nonsense labels ("Frobnicate"). Plausible-but-absent labels would be a harder false-pass test, for VizDOM's OCR as much as for the grounders.
  • ADR-017 still Proposed — the deployability claim is demonstrated, not ratified. Security: gRPC channels are insecure (LAN/trusted only).

Roadmap

Near term

  • Real-world labelled set — the headline accuracy caveat
  • Descriptions by other testers — the desc= column is measured on generated wording; a hand-paraphrase check holds the oracle (0 false passes) at 0.90 action-hit for terse wording and 0.71 for wording that drops the label — wording from people other than the author is the stronger version
  • Harder negatives for the false-pass metric — plausible-but-absent labels ("Export" on a screen with "Import"); the grounder columns themselves are done
  • Defect injection — mutate a state, measure whether the suite catches it: mutation testing for GUI automation
  • Wall-clock comparison of a warm gRPC service against in-process (per-state pipeline cost is already measured)
  • Window-control labeller (canonical minimize/maximize/close)

Longer term

  • Self-healing locators — cache resolved descriptions as aliases so a suite migrates from model-resolved to deterministic over time
  • Embedding tier (semantic similarity, no generation)
  • A dedicated grounder as an alternative Tier-2 backend
  • Hierarchy/locator ground truth → score the remaining two axes
  • TLS + authentication on the service channels

Priority: the real-world labelled set — every caveat on the previous slide points to it, and the benchmark schema, the kit and the desc= chain are ready to take it.

What the application actually does — features

1 · Generate a DOM from a screenshot

Bounds, roles, text, labels, interaction flags (clickable / editable / scrollable), containment hierarchy, and multiple ready-made locators per element — as UI-Automator-like JSON.

2 · Choose your detector

4 backends by name: uied (CPU, no weights), yolo, omniparser (GPU, best on actionable controls), grpc (remote). OCR: EasyOCR / PaddleOCR / Tesseract.

3 · Capture from anywhere

5 sources: windows, linux, android (adb), camera (auto screen rectification), grpc — plus static images and user plugins.

4 · Drive the application

Click, type, key press, scroll, drag & drop via desktop / android / grpc / a robot-arm plugin — all on normalized coordinates, so one test fits every target. Both the capture and actuator ports can also raise the app under test, so the screenshot and the clicks reach it and not the window on top.

5 · Write tests in Robot Framework

28 keywords — Connect, Dump Visual DOM, Click Visual, Type Text Visual, Verify Element Value (re-reads the live screen), Visual Should Exist, Wait Until Visual Appears, Get Element Property/Text/Label/Center, …

6 · Find elements 7 ways — chainable

id= text= hint= role=, spatial (within, right_of, below, …), desc= (plain language) — and || fallback chains: text=Save || desc="save button" tries the cheap deterministic locator first, the resilient one only if it fails.

7 · Configure everything in one file

One JSON session config drives every stage; --init emits an annotated template, --check validates it. No code change to retune a run.

8 · Scale out when needed

Run detector / capture / actuator as gRPC services across machines — one warm GPU model serving many clients — with no change to the test.

9 · Inspect, evaluate, extend

Interactive Viewer (browse and edit the DOM, export RF resources), an evaluation harness (metrics + reports), dataset generators, and plugins — drop in one file. Every run saves a session (screenshot + detections + DOM + the analyzed window title / process) for later comparison.

10 · Names for non-text controls. Icons and glyph keys get semantics from a layered answer: literal glyph reading (+ − = × ÷) into text, caption-derived labels kept separate from read text, canonical names for recognised controls (÷ → “Divide”), and desc= grounding as the escape hatch.

Optional: a small LM/VLM review stage (split / retype / merge / label) and session-based output — every run saves screenshot + detections + DOM for later inspection. Two deliverables: the engine, and the Robot Framework library that consumes it.

Architecture: hexagonal ports & adapters

A pure core depends only on abstract ports:

  • OcrPort · RefinerPort
  • CapturePort — windows / linux / android / camera / gRPC

Strategy + registry + auto-discovery

A user adds a backend by dropping one file into plugins/; the registry loads it and it is selectable by name from configuration — no core changes.

Chosen for testability (core runs with no I/O) and substitutability — the project's primary quality goal. ADR-015 / 017 / 018 / 019.
